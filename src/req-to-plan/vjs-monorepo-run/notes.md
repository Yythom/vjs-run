以下是 vjs-monorepo（光厂 vjshi.com）上实测出来的坑，随 skill 一并注入。

## 需求语言与代码语言的错位

需求文档写业务概念，代码里只有具体控件文案。直接拿业务概念词检索会命中 0：

| 需求里的词 | 代码里实际有的 |
| --- | --- |
| 作品优化 | 优化说明 / 优化记录 / 优化指南 |
| 断点续传 | 暂停 / 继续 |
| 找相似 | （新功能，尚不存在，命中 0 是正确的） |

反过来也有陷阱：`暂停` 不带 `--scope` 会同时命中音乐播放器和广告计划，与上传断点无关。

## 业务线的路径别名

需求池的业务线中文名与代码目录名对不上，`repo.config.json` 里已配好别名。几个实测事实：

- 「服务」线代码里主要写 `demand`（27 个目录），`studio` 只有 49、`service` 21
- 「案例」线代码里主要写 `case`（25）和 `idea`（7），`vision` 只有 3
- 路由参数只有 `$vid`(1) / `$fid`(7) / `$caseId`(6) 三种专属命名，其余 65 个都是通用 `$id`

**mirror 在上传相关路径上不可信**：案例线的上传是 `_simple.user.upload.idea.share`，视频线是
`_simplelanding.user.upload.video`，层级结构本就不同，会把已存在的实现误报成缺失。
这种情况用 `siblings` 按文件名找。

## 需求文档的两种模板

「检查」段在两种模板里都稳定存在，且常被忽略：

| 模板 | 段落 |
| --- | --- |
| A | 定义 / 检查 / 方案 |
| B | 圈定 / 检查 / 调研 |

「检查 → 数据 → 数据埋点」和「检查 → 团队 → 消息更新同步」直接对应埋点与站内信改动，不要漏读。

## 需求池的数据质量

实测 25 条「排实施」需求里：

- 4 条是招聘岗位（业务线=不涉及业务线），不是开发需求
- 2 条业务线填「其他」，但确实要改代码（提现、媒资工具）—— 需人工确认，不能直接跳过
- 1 条方案链接栏填的是 MasterGo 视觉稿而非飞书文档
- 6 条共用 2 份方案文档 —— agent 无法判断该做其中哪一条，工作包里会标出共用者

## 仓库自身的规则

产出 plan 前必读 `AGENTS.md` 与 `docs/rules/*`。几条最容易在 plan 里漏掉的：

- **链接收敛**：`DioaLink` / `RouteLink` / `OutLink` 已禁用，站内路由用 `<Link to>`，
  跨业务线用原生 `<a>`。改动只要 touch 到含旧写法的那一行，就该顺手换掉。
- **表单**：不再新增 `@dioa-ui/react` Form，统一 `@vjs/hook-form` + `zod`
- **Tailwind**：preset 是替换式的，禁止用默认色板与任意 hex；有 token 必须用 token
- **迁移类需求**：`gc-feat-migration`（怎么迁）与 `migration-review`（怎么验）成对使用

## 已知的仓库瑕疵

- `apps/foto` 是残留空壳目录（只剩 node_modules），扫描时已自动排除，不要当成第 8 个应用
- 部分组件内部命名与所在业务线不符，例如图片优化页里的组件仍叫 `VideoUpload`
