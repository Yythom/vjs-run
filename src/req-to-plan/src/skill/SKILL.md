# 需求 → 实施 plan

## 触发边界

**用本 skill：**

- 需求池里状态为「排实施」的需求要进入开发
- 需求评审阶段想提前知道影响面、接口缺口、待澄清项
- 判断一条需求能否交给子 agent 自动实施

**不用本 skill：**

- 已经有 plan，直接写代码 → 按 plan 走对应的实现类 skill
- 临时改一两行文案且已知改哪 → 直接改
- 需求还没定稿（状态不是「排实施」）→ 不要提前生成 plan，需求还会变

## 环境变量

本 skill 由 `req plan` 注入，运行时可用：

- `$REQ_BIN` —— 工具入口（形如 `node /path/to/req-to-plan/bin/req`）
- `$REPO_ROOT` —— 被分析仓库根目录
- `$WORKPACK` —— 当前工作包目录，产出的 plan 写到 `$WORKPACK/plan.md`
- `$API_SEARCH` / `$API_DETAIL` —— 项目的接口检索命令（未配置时为提示语）

影响面命令若不在仓库目录下执行，需补 `--repo $REPO_ROOT`。

## 执行流程

### 步骤 1: 取需求

```bash
$REQ_BIN pool
```

输出「排实施」状态的全部需求，每条含业务线（已映射成仓库 token）、方案链接、视觉稿链接、record_id。

**业务线以这里的字段为准，不要从需求文档里猜。** 它是结构化的多选字段，直接给出扩散范围。

分诊第一刀在这里就能落：业务线为「不涉及业务线」的（招聘、流程类）不是开发需求，直接跳过。

### 步骤 2: 读需求文档

```bash
$REQ_BIN prepare <链接|record_id> --out <工作包目录>
```

产出 `requirement.md`（树形，agent 直接读）、`requirement.json`（结构化）、`assets/`（图片）。

**必须读图。** 界面细节大量只存在于截图里——尺寸上限、字数限制、按钮态、空态文案，正文一个字都不会写。用 Read 逐张看 `assets/` 下的图。

需求文档常见两种模板，「检查」段稳定存在：

| 模板 | 段落 |
| --- | --- |
| A | 定义 / 检查 / 方案 |
| B | 圈定 / 检查 / 调研 |

「检查」段里的「数据 → 数据埋点」「团队 → 消息更新同步」直接对应埋点与站内信改动，不要漏读。

### 步骤 3: 提取检索词与范围

这一步是判断，做不好后面全废。

**需求语言 ≠ 代码语言。** 需求写业务概念，代码写界面文案；本项目已知的词汇错位见文末「项目经验」。

先用需求里的**具体控件文案**和**页面名**检索，命中 0 时逐步缩短成词根，不要在业务概念词上反复试。

**范围必须限定。** 从需求提到的页面推出目录前缀（「上传页/作品优化页」→ `upload,optimization`）。不带范围的检索会把音乐播放器的「暂停」和上传断点的「暂停」混在一起。

### 步骤 4: 算影响面

```bash
# 关键词检索 + 孪生展开（--scope 强烈建议带上）
$REQ_BIN scan locate "<词>" "<词>" --scope "<前缀,前缀>"

# 业务线对称：源业务线已有、目标业务线缺什么
$REQ_BIN scan mirror "<路径前缀>" --from video --to foto
# 同名不同路径的实现（twins 覆盖不到的一类重复）
$REQ_BIN scan siblings "<仓库相对路径>"
```

三个输出各自回答一个问题：


- `locate` → **要改的现存文件**，以及每个文件在几个 app 各存一份
- `mirror` → **要新建的文件**，以及每个文件照着谁写
- `siblings` → **同一份逻辑还有几份拷贝**，按上下文相似度排序

`locate` 报「需改 N 处」时那 N 处都要进 plan。本仓库存在大量跨 app 孪生文件（规模见文末「仓库现状」），漏改一处 typecheck 不会报错。

**`locate` 命中的每个文件都要再跑一次 `siblings`。** `twins` 只认跨 app 的同路径拷贝，而同一份逻辑在不同路由下各写一份它认不出来。`siblings` 输出的相似度可直接用来判断能否机械复制：0.9 以上通常结构一致，0.7 以下要单独确认。

#### 业务线与它们在代码里的别名

需求池写业务线的中文名，代码里未必用同一个词（对照表见文末「仓库现状」）。

`mirror` 已内置这套别名：生成目标路径用主 token，找不到时用别名再探测一遍，命中会标出「目标侧命名为 xxx」。

**`mirror` 的前缀要给具体功能名，不要给宽泛词。** `mirror "optimization"` 有意义；`mirror "upload"` 会把 ffmpeg、播放列表封面之类完全不相干的文件也算成「缺失」。

**`mirror` 只在路径结构对称时可信。** 两条业务线的目录层级本就不同时，它会把已存在的对应实现误报成缺失 —— 此时改用 `siblings` 按文件名找。

### 步骤 5: 对接口

```bash
$API_SEARCH "<业务关键词>"
$API_DETAIL "<接口路径>"
```

对 plan 里每个要读写数据的位置，确认接口存在、字段够用。

**这一步必须在开工前做完。** 接口缺口是整条链路最贵的返工点——它要等后端排期，而不是改几行代码。查不到就写进澄清清单，标明「需提接口需求」。

### 步骤 6: 产出 plan

按 [`assets/plan-template.md`](assets/plan-template.md) 组织，落到 `.requirements/<slug>/plan.md`。

## 分诊：能不能自动实施

plan 必须给出分诊结论。判据是**成功标准能否被机器判定**，不是任务大小。

| 类型 | 判据 | 结论 |
| --- | --- | --- |
| 横向复制 | `mirror` 给出明确参照，且缺失文件多为结构对称 | 可自动 |
| 纯文案 / 跳转参数 | 改动限于字符串与拼接，有孪生清单兜底 | 可自动 |
| 迁移类 | 项目已有「怎么迁」+「怎么验」成对的规范 | 可自动 |
| 新建表单 / 校验 / 交互 | 字段规则来自 UI 稿与产品判断，无参照可比对 | 需人工 |
| 接口未就绪 | 提交体结构未定 | 阻塞，先提接口需求 |

同一条需求通常两者都有。`mirror` 的 `matched` / `missing` 天然把它切开：结构对称的部分可自动，目标业务线特有的部分需人工。

**把这条线画在 plan 里，比给一个笼统的「可以/不可以」有用得多。**

## 红线

- **不要跳过澄清清单。** 需求文档自己标注的「开发阶段确认」项必须逐条抄进去。缺澄清项的 plan 会让子 agent 靠猜补齐。
- **引用图里的信息必须标来源。** UI 稿会过期——曾出现图上写「27/100」而实现是 `max(300)` 的情况。凡是只在图里出现的约束，标「来源：UI 稿，需确认」。
- **业务线不从文档推断。** 以需求池字段为准。
- **不要在 plan 阶段改代码。** 本 skill 只产出计划。
- **需求状态不是「排实施」就不生成 plan。** 定稿前的需求还会变。

## 检查清单

- [ ] 图片逐张读过，界面约束已提取
- [ ] 检索带了 `--scope`，命中结果与需求描述的模块一致

- [ ] `locate` 命中的文件都跑过 `siblings`，同名实现已逐一核对

- [ ] 澄清清单含需求文档自标的待确认项
- [ ] 给出了分诊结论及理由
