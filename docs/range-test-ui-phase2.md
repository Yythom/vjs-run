# 改动测试台 · 第二期实现方案

第一期解决「怎么发起、怎么回复确认点」。第二期解决**确认开测之后**的事：测的过程中看什么、停了怎么接着测、测完怎么收尾、修完怎么回归。

定位不变：vjtools 不跑 AI，只调 `t3`、读产物文件、渲染界面；规则只在 skill 里；状态以产物文件为准。

## P0：跑通第二阶段

拿第一期 e2e 留下的 `e2e-最近1个`（robots.txt，5 条 × 2 站）点「确认开测」。agent 自己评估过：不需要 mock、不需要登录 cookie、不动场景，10 分钟内。

要记下来的事实（决定 P1 的细节）：

- log 实际写成什么样：`### A1 · 视频` 标题、`测试提交：<sha>` 行、正文里放了什么（curl 输出、history 编号、截图路径）
- 截图落在哪：T3 自带浏览器的截图默认在 `~/.t3/userdata/browser-artifacts/`，不在产物目录
- 格子刷新节奏：agent 是测一格写一格，还是攒一批再写（影响文件监听推送频率）
- 一轮结束时 `status` 有没有报证据问题、最后一条消息是不是第 8 步报告
- 跑多久、中途会不会因为额度停下

跑完把结论补进本文档「已实测的前提」，再动 P1。

## 已实测的前提（M0，2026-11-24）

拿 `e2e-最近1个`（`1a0fbcbf26..c53d3edec2`，robots.txt，5 条 × 2 站）在界面上点了「确认开测」，DeepSeek 4.1，**201 秒**跑完。结果：✅ 7 · — 1 · ⬜ 2（两格都是【线上】的 A6），`status --log --map` 没有报问题，agent 最后一条消息是完整的第 8 步报告。

## P1：证据面板

### skill 侧：`status --json` 带上每格的证据

`status --log --map` 已经能判断每格证据的问题（缺证据、空话、没写测试提交、过期、提交找不到），但只汇总成文字。`--json` 时把它落到每一格上：

```json
"results": [
  {
    "site": "视频", "state": "pass", "text": "✅",
    "evidence": {
      "state": "ok",
      "sections": [
        { "heading": "A1 · 视频", "commit": "c53d3edec2", "voided": false, "line": 42, "body": "…" }
      ]
    }
  }
]
```

- `evidence.state`：`ok` / `missing` / `empty` / `no-commit` / `stale` / `lost` / `none`（⬜ 和 — 的格不要求证据）
- `sections`：这一格在 log 里的所有段落，包括标了作废的（`voided: true`），按出现顺序排列。正文原样给出，界面负责渲染
- 另加 `testedHead`：从清单头「实测代码：HEAD `<sha>`」（或 `<旧> → <新>`）里解析出来的当前实测提交，回归时要用

改动在 `parseLogEvidence` 里顺带收集段落正文，不新写一套 log 解析；补 `coverage.test.mjs` 用例。

### 截图：靠提示词约定，不改 skill

确认开测的回复里加一句：「截图存到产物目录的 `evidence/` 下，在 log 里用相对路径 `![](evidence/A1-视频.png)` 引用」。这样截图和记录在同一个目录里，界面只需读产物目录。

主进程加 IPC `range-test-asset { dir, path }`：只允许读 `<dir>` 下面的文件（`assertRecordDir` 加路径归一化，防 `../`），返回 data URL。不在产物目录里的图片路径照原文显示，提供「在访达中显示」。

### 界面

- **格子标记**：`evidence.state` 不是 `ok` / `none` 时，格子右上角加一个小点，悬停显示原因（「打了 ✅ 但 log 里没有证据」「证据过期：测完后 xxx.tsx 又改过」）
- **证据抽屉**：点格子，右侧滑出抽屉，按段落显示 markdown 正文（作废的段落折叠、灰显），图片内联显示
- **markdown 渲染**：引入 `react-markdown` + `remark-gfm`（表格、代码块），放在 range-test 的 lazy chunk 里，不进主包。默认不渲染原始 HTML，没有 XSS 面

## P1：确认后改动追踪

M0 里 agent 在第二阶段改了两条已确认行的「前置」和「预期」。改得有道理，但使用者确认的是原来那版，应该让他看得到改了什么。

- 点「确认开测」时，主进程把当时的清单复制成 `<产物目录>/.vjtools-confirmed-checklist.md`，sidecar 记下路径和时间
- 详情页对比快照和当前清单，按编号逐列比较：改过的格加底色，悬停显示原来的内容；删掉和新增的行单独列出
- 比较只看「前置 / 操作 / 预期 / 原来怎样」这几列，结果格不算（结果格本来就要变）
- 只在确认开测时拍快照：使用者批准的是那一版，「继续测」「回归」再拍会把之前的改动藏掉

## P1：运行控制

线程一轮结束（`state = idle`）而阶段是「已确认」时，详情页根据文件状态给出下一步按钮。都是往同一个线程 `send` 一条消息，复用第一期的回复机制：

| 条件（全部从文件和线程状态推出） | 按钮 | 发出的消息要点 |
|---|---|---|
| 还有 ⬜ 格（不算标了【测试服】【真机】【线上】的行） | **继续测** | 从还是 ⬜ 的格接着做第 7 步，做完照第 8 步收尾 |
| `status` 报了证据问题 | **修正证据问题** | 原样带上 `status` 的 problems 列表，让 agent 逐条处理 |
| 没有 ⬜、没有证据问题 | **回归**（修完 bug 后用） | 做第 9 步；附上修复提交列表 |
| 线程失败 / 找不到 / 已经跑了很多轮 | **换新线程续接** | 新起线程：「读产物目录 X，按 SKILL.md 中断续测的规矩接着做，阶段已确认，不重做第 1～5 步」 |

### 回归的修复提交

点「回归」先弹一个小确认框：主进程算出 `git log <testedHead>..HEAD`，列出这之后的提交让使用者勾选哪些是修复，再发消息。没有新提交时按钮置灰，提示「实测之后还没有新提交」。

### 换新线程

skill 本身支持从产物文件续接（看「阶段」行，从 ⬜ 的格做起），所以线程丢了或上下文太长都不怕。sidecar 把 `threadId` 改成当前线程，旧的追加进 `threads: [{ threadId, link, startedAt, endedAt }]`，详情页能看到历史线程链接。

「跑了很多轮」的阈值先定 `runCount >= 8`，只作提示，不强制。

## P2：报告视图

第二阶段结束（已确认 + 线程 idle + 没有 ⬜）时，详情页顶部换成报告卡：

- **结论条**：`已出结果 x/K 格`，✅ / ❌ / — 各多少，证据有无问题，数据来自 `status --json`
- **不通过**：❌ 的格，点开看证据
- **没测到**：⬜ 格（按「使用者定的」和「其他原因」分组）、标了【测试服】【真机】【线上】的行、— 的格及原因
- **agent 的报告原文**：最后一条消息用 markdown 渲染（「其他发现」「留下的东西」都在里面，不再另行解析）

第一期里所有显示 agent 消息的地方都换成 markdown 渲染。

## P2：mock 场景收尾

skill 规定 agent 不删场景，留给使用者定。这正是 vjtools 自己的功能，可以直接接上：

- 详情页加「mock 场景」卡片：当前生效的场景；这次测试相关的场景，即名字是 `测试-<主题>` 的，以及名字出现在 log 里的 `备份-…`
- 按钮：**应用**（切回原场景）、**删除**（二次确认），复用已有的 IPC `apply-mock-scene`、`delete-mock-scene`，不新增接口
- 线程还在跑时按钮置灰，防止和 agent 抢着改场景

## P2：小件

- **一轮结束通知**：轮询器发现 `running → idle / failed / needs-answer` 时，调用已有的 `services/notify.js` 发系统通知（「e2e-最近1个：已到确认点 / 第二阶段跑完 / 失败了」）。第二阶段动辄十几分钟，不用一直盯着
- **列表页进度**：每条记录显示一个进度条（✅ / ❌ / ⬜ 比例）。`listRecords` 对有清单的记录跑 `status --json`，按清单 mtime 缓存，没变就不重跑
- **确认前查端口**：点「确认开测」时查一遍常用 dev 端口（5173 等，取自 `vjs-setup.md` 的端口表）的占用进程，把「哪些端口被什么占着、不要停」预填进补充说明。M0 实测过，agent 会照这句做
- **skill 版本检测**：打开改动测试页时检查 `coverage.mjs --help` 里有没有 `--json`；没有就在页面顶部提示「skill 版本不含 --json，清单显示不了，更新 commit-range-test」。skill 目录不在版本控制里，被同步覆盖时能马上发现

## M1 结果（2026-11-24）

改动都在 skill 的 `scripts/coverage.mjs`（`~/.config/magpie/library/skills/commit-range-test`，不在 git 里；改前的版本备份在会话草稿目录）：

- `status --json` 带 `--log --map` 时，每个结果格多一个 `evidence: { state, commit?, changed?, sections }`。`state` 取 `ok` / `missing` / `empty` / `no-commit` / `stale` / `lost` / `none`；`sections` 是 log 里能对上这一格的所有段落 `{ id, heading, voided, commit, line, body }`，作废的也在里面
- 顶层加 `testedHead`：清单头「实测代码」最后一次出现的提交，带箭头时取箭头后面的
- 不带 `--log` 时输出和以前一样，没有 `evidence` 字段；文字输出（不带 `--json`）在 M0 的记录和 124 条的 `latest-10-commits` 上和改动前逐字一致
- `coverage.test.mjs`：20 → 21 个用例，全部通过

**顺带修掉一个第一期就有的 bug**：`--json` 在 `console.log` 之后马上 `process.exit()`，stdout 是管道时（macOS 上是异步写）大段 JSON 会被截断，读的一方拿到的是半截。124 条的清单实测在 45 KB 处被截断，也就是说第一期在 app 里打开大清单的详情页会读失败。现在改为设置 `process.exitCode` 后自然退出，出错时的 `die` 改用同步写。新增的大输出用例在旧写法下会失败（实测截断在 45720 字节），新写法下通过。

## M3 结果（2026-11-24）

- **下一步卡片**：线程这一轮结束且清单已确认时出现，按文件状态给按钮：

**SEO robots 404 的核实（只读）**：`www.vjshi.com/so/robots.txt` 确实 404。原因是 SEO 应用挂在 `/so` 前缀下，而 `server.js` 的 `serveStatic({ root: 'build/client' })` 按原路径找文件，找的是 `build/client/so/robots.txt`。但爬虫只读域名根路径的 `robots.txt`：`www.vjshi.com/robots.txt` 是视频站那份，已经带上 AI 训练那一组，覆盖整个域名（包括 `/so/*`）。`so.vjshi.com` 会 301 到 `www.vjshi.com/so/…`。所以 SEO 的 `public/robots.txt` 只是一份不会被读到的冗余文件，不是「规则没生效」。agent 说「`server.js` 整份被注释、没有静态中间件」不准确：它前 112 行是注释，后面是生效代码。
